---
title: INNER JOIN
description: Return only the rows that match in both tables — and know when a non-unique key silently duplicates them.
---

## Syntax

```sql
SELECT ...
FROM left_table lt
INNER JOIN right_table rt
  ON lt.key = rt.key;
```

`INNER JOIN` and plain `JOIN` are the same thing — the `INNER` is optional.

## What it does

Keeps only the rows with matching keys in both tables. It's the default join
when you're filtering to relationships that actually exist.

## Example

<SqlRunner query={`SELECT
  c.customer_id,
  c.name,
  o.order_id,
  o.amount
FROM customers c
INNER JOIN orders o
  ON c.customer_id = o.customer_id
ORDER BY c.customer_id;`} />

Customers 6 and 7 (Wayne Enterprises, Soylent) have no orders — they simply
don't appear. That's `INNER JOIN`'s defining behavior; if you need them anyway,
that's a [LEFT JOIN](/docs/joins/left-join).

## Fan-out: the row count can grow

If the right table has more than one matching row per key, the left row repeats
— once per match:

<SqlRunner query={`SELECT c.customer_id, c.name, COUNT(o.order_id) AS matched_orders
FROM customers c
INNER JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id;`} />

Customer 1 has 3 orders, so joining `customers` to `orders` on `customer_id`
turns that **one** customer row into **three**. This is correct when you want
one row per order — but if you then `SUM()` a customer-level column without
grouping, you'll silently multiply it. Always check the row count against what
you expect before trusting a join's aggregate.

## Safety check before shipping

- confirm the join key represents the intended relationship
- inspect row counts before and after the join
- decide whether duplicates (fan-out) are valid or indicate a broken relationship
